# 汎用表検算の精度と、有料LLMとの比較（2026-11-27）

## 結論

- **表の検算**は、誤りを仕込んだ表の最終評価（一度も調整に使っていない68表）で、**誤りの検出率 91.5%（43/47）、誤りのない表での誤検知 0%（0/21）** でした。
  Excel で作ったような「丸める前の値から計算した表」でも、誤検知は 0/68、検出率は 87%（40/46）です。
- **有料LLM（Claude Opus 5.5、コード実行なし）** に同じ形式の24表を解かせると、19/19 の誤りを見つけ、誤検知も 0/5 でした。
  同じ24表で、改良前のツールは 16/19、改良後は 19/19 です。**表の算術だけなら、時間をかけて丁寧に検算させたLLMとほぼ同等**です。
- 差が出るのは算術の正しさではなく、**再現性・コスト・規模・文脈理解**です（下の「得意・不得意」）。
- **独自性スコアの精度は、人間の評価データがないため比較できません。** ここは有料LLMに評価させた方が現状では妥当だと考えます。

## ベンチマークの作り方

`validation/table_bench.py`。17種類の実験テンプレート（オームの法則、単振り子、密度、ばね定数、温度換算、吸光度、中和滴定、自由落下、X線回折、屈折率、運動エネルギー、誤差率、熱量、凸レンズ、単位換算、繰り返し測定の平均・標準偏差、収率）から表を作り、約65%の表に1つだけ誤りを入れます。

| 誤りの種類 | 内容 |
| :--- | :--- |
| calc | 計算列の値が3〜9桁ぶんずれる |
| transpose | 計算列の数字の入れ替え（18.9 → 81.9） |
| input | 入力列の転記ミス（その行の計算が合わなくなる） |
| unit10 | 1行だけ10倍・1/10 |
| lastdigit | 最終桁が2ずれる（丸めでは説明できない最小のずれ） |
| summary_mean / summary_sd | 平均行・標準偏差行の誤り |
| deg_rad / two_theta | 列全体を度/ラジアン取り違え、2θ をそのまま使用 |

採点は表単位です。誤りのある表では正しい行（列全体の誤りなら列単位の指摘）を WARNING 以上で示せたら検出、誤りのない表で WARNING 以上を出したら誤検知です。

### データの分け方（チューニングの持ち込みを避けるため）

| 分割 | シード | 用途 | 結果 |
| :--- | :--- | :--- | :--- |
| dev | 1001 | 開発・調整 | 調整後 100% / 誤検知 0% |
| test | 20261127 | LLMとの比較に使用。のちに失敗例を分析したので評価には使わない | 97.9% / 0% |
| final | 777 | 初回 88.6% / 0%。ここで見つかったバグ2件を直したので評価には使わない | 修正後 100% / 0% |
| **holdout** | 9090 | **すべての修正の後に1回だけ実行** | **91.5% / 0%** |
| excel | 4242 | 丸める前の値から計算した、誤りのない表68個 | 誤検知 0% |
| excel_err | 5151 | 丸める前の値から計算した表に誤りを入れたもの | 87.0% / 0% |

holdout の見逃し4件の内訳は、lastdigit が3件、calc が1件です。どちらも入力の丸め幅の中に収まり、表示された値だけからは誤りと言い切れないずれでした。lastdigit を除いた検出率は 97.6%（40/41）です。

## 有料LLMとの比較

- 対象：test 分割の最初の24表（誤りあり19、誤りなし5）。
- LLM：Claude Opus 5.5。コード実行なし。正解キーとツールの結果を見る前に、1表ずつ暗算で検算させた回答を `table_bench/llm_claude_no_tools.json` に保存しています。
- 再採点：`python validation/table_bench.py --split test --llm validation/table_bench/llm_claude_no_tools.json`

| | 検出 | 誤検知 |
| :--- | :--- | :--- |
| LLM（コード実行なし） | 19/19 | 0/5 |
| ツール（改良前） | 16/19 | 0/5 |
| ツール（改良後） | 19/19 | 0/5 |

改良前のツールは、最終桁のずれ（入力の丸め幅の中には収まるもの）を「矛盾とは言い切れない」として見逃していました。LLMは「学生は表示値から計算する」という前提で読むので、これを拾えていました。そこで、**表の他の行がすべて表示値から最終桁まで一致する（手計算の表だと分かる）ときだけ、1行の最終桁のずれを指摘する**判定を足しました。Excel風の表で誤検知が出ないことは excel 分割で確かめています。

### この比較の弱点（割り引いて読むべき点）

- LLM役は、ツールを作ったのと同じモデルで、誤りの種類を知っていました。行の位置は知りません。一般の利用者が普通に聞いたときの回答より有利な条件です。
- LLMは1回だけ、時間をかけて丁寧に検算した結果です。LLMの暗算は回ごとに結果が変わり、ときどき自信をもって計算を間違えます。今回はそれが起きませんでしたが、1回分なので保証にはなりません。
- GPT系など他社のモデルは、APIキーがないため試していません。
- 表は合成データで、テンプレートも同じ作者が作っています。実レポートの表（結合セル、単位が行ごとに違う、3列以上をまたぐ式など）では、どちらの成績も下がるはずです。

## 得意・不得意

| | ツール（決定論的） | 有料LLM |
| :--- | :--- | :--- |
| 表の算術（数行〜十数行） | 同等 | 同等（丁寧に検算させた場合） |
| 再現性 | 毎回同じ結果。同じ入力で結果が変わらない | 回ごとに変わる。計算ミスを自信をもって言うことがある |
| 「丸めの範囲内か」の判断 | 丸め幅を伝播させて数値で判定。言いがかりを出しにくい | 感覚的。境界のケースで揺れる |
| 長い表・大量のファイル | 一瞬・無料・オフライン | 行数が増えるほど見落としと費用が増える |
| 個人データ | 外に出ない | 送信が必要 |
| 文脈の理解 | 列の数値だけを見る。説明文に書かれた式は読まない | 「f = ab/(a+b) を求めた」などの説明から式を理解できる |
| 列全体が同じ誤り | 度/ラジアン・2θ/θ・単位換算の桁ずれだけ検出 | 物理的な妥当性（g = 0.98 は変、など）から気づける |
| 3列以上・表にない定数が2つ以上の式 | 推定できない | 説明があれば検算できる |
| 考察・文章の質 | 独自性スコアは参考値（未検証） | こちらが上と考えるのが妥当 |

## おすすめの使い方

MCP サーバーとして Claude などから呼び、**LLMが文脈を読み、算術はツールに任せる**のが両者の強みを活かせます。
`check_table_generic` は推定した計算式（relations）も返すので、LLM はどの式で検算したかを確認したうえで説明できます。
